# 宽高比补偿

## 问题

终端字符格约 **1:2** 的宽高比（宽约为高的一半）。把数据坐标直接 1:1 映射到格坐标，
圆会画成竖椭圆、正弦波会被纵向拉伸一倍。

## 决策

- 所有取景/布局代码按「宽格数 ≈ 高格数 × 2」的直觉换算，把字符格比当作布局常数；
- 文档约定（CODEBUDDY.md 坑 11）：画图前必须用 `terminal.size()` 自适应——
  宽取 `cols`、高取 `rows - 1`（留一行给提示符），并按约 1:2 等比取景，否则
  超宽折行 + 超高滚动叠加会让图像整体错位（看起来像"颜色溢出"，甚至顶部截断）。
- 极坐标图表（pie/donut/radar/gauge 等）在内切椭圆上做归一化：以「格坐标下的圆」
  为准做解析落格，而不是先画圆再缩放。

## 体现位置

- `layout/PlotArea`（layout/box.hpp）：绘图区矩形即按格粒度规划；
- 各极坐标图表：圆盘/环/弧都是格粒度解析填充或按角度采样（见 design/rasterization.md）；
- `image/` 与 `protocol/`：位图路径不受字符格比影响（像素级输出），
  半块字符显示时天然 1:2（一个 ▀ 覆盖上下两"像素行"），恰好补偿。

## 反例

- 把画布尺寸写死成大于终端可视区：折行 × 滚动 → 图像错位；
- 假设字符格是方的：需要圆的东西全部变形。

## 未做

规格中若有按 DPI/字符格实测的自适应补偿（查询真实 cell pixel size），当前
公开头里没有对应 API；现状是按 1:2 常数处理。
